# Mosaic response

**Task:** Should we adopt event sourcing for our user activity log? Team is 6 engineers, primarily backend, no event-sourcing experience. Activity volume is 100k events/day growing 20% q/q. No audit/compliance requirement today but possibly within 18 months.


## technical_tradeoffs *(voice: codex)*

I couldn’t find an actual repo in `/private/tmp` to anchor this to, so my slice is based on the stated system shape. At 100k events/day, volume is not the reason to choose event sourcing. Even with 20% quarter-over-quarter growth, the log is roughly 49M events in year 1, 90M over 18 months, and the daily rate reaches about 300k/day by then. At 1-2 KB/event before index/WAL/replication overhead, that is probably tens to low hundreds of GB raw, and a few hundred GB to around 1 TB operationally depending on indexes, replicas, and retention. That is very manageable for an append-only table partitioned by time, with indexes for the real access paths: `user_id + occurred_at`, maybe `actor_id`, `entity_type/entity_id`, `event_type`, and coarse time filters. The scaling problem is more about query design, retention, and backfills than write throughput.

The key distinction: event sourcing makes the activity event stream the source of truth for domain state. That buys deterministic reconstruction, temporal state inspection, replay into new projections, stronger audit semantics, and the ability to rebuild read models from first principles. But it also imposes permanent event contracts, versioned event schemas, upcasters, idempotent projection handlers, replay tooling, ordering guarantees, snapshot strategy for long streams, and operational discipline around “bad events” that cannot simply be updated away. For a 6-engineer backend team with no ES experience and no audit requirement today, that is a large structural commitment for capabilities the activity log likely does not need.

The middle ground I’d recommend the doer synthesize around is: use an explicit append-only `activity_events` table now, written transactionally from the code paths that know the business meaning, and pair it with a transactional outbox if downstream consumers/search/analytics need reliable async delivery. CDC is useful as plumbing, but weak as the semantic source for an activity log because row changes rarely map cleanly to user-intent events. This preserves most near-term value: user timelines, entity timelines, admin search, exports, retention controls, and future audit hardening. If compliance becomes real in 18 months, the append-only table can evolve toward stricter immutability, signatures/checksums, retention policies, and external archiving without forcing the whole domain model into event sourcing now.

## team_readiness_and_adoption_risk *(voice: claude)*

Six backend engineers, zero ES experience, and you're asking what the next 9 months look like. Honestly: the learning curve isn't the scary part. Engineers can read Greg Young's talks and Vaughn Vernon in a few weeks, and the *mechanics* of append-only logs and projections click pretty fast. What doesn't click fast — and what burns teams — is the *judgment*. Specifically: knowing when an event is "right." With CRUD, wrong is loud (the row is wrong, the test fails, the customer complains). With ES, wrong is quiet. A projection that double-counts because the team didn't realize a retry path was at-least-once. An event named `UserUpdated` with a payload bag instead of `EmailChanged` / `RoleAssigned` — works fine for six months, then someone needs to replay and discovers the events don't actually carry enough semantic meaning to reconstruct intent. These are the bugs nobody catches because nobody on the team has the muscle memory for what right looks like, and code review doesn't surface them because the reviewer is learning too.

The expensive-to-undo class is worse than people expect. Event schemas are forever in a way that DB schemas aren't — once events are in the log and projections depend on them, "let's just change the shape" means an upcaster, or a versioned event, or a full replay against a parallel projection. A team without ES reps will ship the v1 schema, discover in month 4 that they modeled state transitions instead of business intents, and then face a choice between living with the mistake or building infrastructure (upcasters, event versioning conventions, replay tooling) that they didn't budget for. The fix isn't hard for an experienced team. It's *demoralizing* for an inexperienced one because it feels like punishment for shipping.

On-call gets weirder, not necessarily worse. The new failure modes are: projection lag (the read model is stale and nobody notices until a customer does), poison events (one bad event halts the projector and now you're debugging a serialization error at 2am with no runbook), and "the projection rebuilt wrong and we don't know which version of the projector code produced the current state." At 100k/day you're not facing scale problems — you're facing *observability gap* problems, which are arguably harder because they don't show up in load tests. Plan for: projection lag dashboards, a poison-event quarantine pattern, and a rebuild procedure documented before you need it. If those three aren't in the design doc, the on-call story is "page someone who read the Greg Young talk most recently."

Hiring signal is mixed and probably net-negative for a 6-person backend team. ES on the resume is a small positive for senior backend hires who've seen it, but it shrinks the pool of mid-level candidates who can be productive in week 2. More importantly, it concentrates knowledge: the one or two people who internalize the event model become load-bearing in a way that's hard to unwind. If either leaves in the next 18 months, the remaining team inherits a system whose core abstraction they don't deeply own.

What "we tried event sourcing" sounds like in 9 months, in the bad case: "We have an events table and a projections service, but we're also dual-writing to a regular users table because the read model was getting stale and nobody had time to fix the projector. We stopped adding new event types six months ago because the schema review got contentious. The replay script exists but nobody's run it in production. New hires take 6 weeks to ship their first feature in this area." That's not catastrophe — it's the much more common outcome, which is a system that nominally uses ES but has accreted enough escape hatches that you're paying the complexity tax without getting the benefits. The good case requires one person who has done this before, owns the patterns, and has the authority to say no to shortcuts. You don't have that person.

My read for the synthesis: the adoption risk here is high enough that if the audit/compliance driver isn't real *today*, the answer is probably "not yet." If it becomes real in 12-18 months, an append-only audit log (just the log, no projections, no CQRS) gets you 80% of the compliance value at maybe 15% of the team-readiness cost — and leaves the door open to fuller ES later if you actually need it. Worth asking the doer: is the team pulling toward ES because it's the right fit, or because it's intellectually exciting? The honest answer changes the recommendation.

## decision_framing_and_deferral *(voice: claude)*

Frame this as "buying the option, not the product." The honest version of the call is: event sourcing is a large architectural commitment with a real learning-curve tax on a team with zero ES experience, and the only forcing function on the table is a *possible* compliance ask 18 months out. That's not enough signal to pay the cost now — but it is enough signal that you shouldn't paint yourself into a corner. So the decision isn't "yes ES" vs "no ES," it's "what's the cheapest thing we can do today that keeps ES on the table tomorrow without pretending we've adopted it?"

Concretely, the reversible "not yet" has two layers worth pricing separately:

1. **Append-only activity table, designed like a log.** Immutable rows, monotonic sequence, server-assigned timestamp, a typed `event_type` + versioned `payload` (JSON), an `actor_id`, and a stable `aggregate_id` (whatever the activity is "about" — user, account, document). No updates, no deletes, no soft-delete flag. This is ~1–2 sprints of discipline, not an architecture. It gives you the audit substrate for free and makes a future replay-from-log story plausible.
2. **Outbox now, only if you already have a second consumer.** If activity is currently written in the same transaction as something downstream cares about (search index, analytics, notifications), an outbox is cheap insurance and decouples writers from consumers. If you don't have that second consumer yet, skip it — outboxes added speculatively become dead code that rots.

Skip the rest of the ES machinery (aggregates rebuilt from events as source of truth, snapshots, projections, command/event split). That's where the learning tax lives, and you have no forcing function for it.

**Revisit triggers — write these down, not just say them.** Make them observable so the team isn't relitigating the decision every quarter:
- Compliance ask moves from "possibly" to "scoped" (named regulation, named auditor, or signed customer contract requiring it).
- A second team needs to consume activity events in near-real-time (the moment you have ≥2 independent consumers, eventual-consistency tradeoffs start mattering).
- Event volume crosses ~1M/day sustained (your 100k × 1.2^q hits that around q6–q7, so ~18 months — convenient alignment with the compliance horizon).
- You hit a case where you genuinely need to answer "what did the system believe at time T" and the current model can't.

Any *one* of those flips the conversation from "defer" to "actively evaluate." Until then, the append-only table is doing the work.

**How to describe it to stakeholders so it doesn't read as ducking:** lead with what you *are* doing, not what you're declining. "We're building the activity log as an immutable, append-only event record from day one. That covers today's needs, gives us a clean audit trail if compliance lands, and means adopting full event sourcing later is an incremental step rather than a rewrite." Then name the triggers explicitly so the deferral has teeth: "We'll revisit if [list]." That reframes it from "the team isn't ready" (true but defensive) to "we've chosen the smallest reversible step and defined what would change our minds" (same decision, but it shows you costed the alternatives).

One thing worth flagging to whoever's owning the cost/complexity slice: the biggest hidden cost of *partially* doing ES is cargo-culting the vocabulary without the discipline — calling rows "events" while still mutating them, or building "projections" that are just views. If you go with the append-only table, the team needs to actually treat it as immutable (enforced at the DB level: revoke UPDATE/DELETE on the role the app uses). Otherwise you get the worst of both worlds: ES-shaped code that doesn't give you ES's guarantees.
