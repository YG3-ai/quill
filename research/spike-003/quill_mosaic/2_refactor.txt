# Mosaic response

**Task:** I have a function that handles user signup, email verification, AND initial password setup all in one. Help me decompose it — proposed split, ordering of changes, what could go wrong.


## decomposition_and_boundaries *(voice: codex)*

The fused function has three separate lifecycle transitions hiding inside it: identity creation (`email` becomes a durable `user` record), email possession proof (`pending_verification` becomes `verified`), and credential activation (`verified` becomes `active` once a password hash exists). I’d split those boundaries explicitly: `signupService.startSignup(input: {email, profile?}) -> {userId, status, emailDeliveryStatus}` creates or finds the pending user and issues a verification challenge; `verificationService.verifyEmail(input: {token}) -> {userId, status}` consumes a single-use token and marks the user verified; `passwordSetupService.setInitialPassword(input: {userId, password, verifiedSessionOrSetupToken}) -> {userId, status}` writes the password hash and activates the account. Keep mail sending outside the DB transaction, but persist enough intent first that a failed send can be retried without orphaning the signup.

I’d model this as `users.status enum('pending_verification','verified','active','disabled')`, `users.email` unique on normalized email, nullable `password_hash` until activation, and a separate `email_verification_tokens` table with `id`, `user_id`, `token_hash`, `expires_at`, `used_at`, `created_at`, maybe `purpose`, plus a uniqueness constraint that allows at most one active token per user/purpose if that matches the product. Store only a hash of the token. Signup transaction: upsert/find user by normalized email, if `active` return generic “check email or login” behavior depending on UX/security stance, if pending/verified issue or reuse/rotate a token, commit, then enqueue/send email. Verification transaction: hash submitted token, lock matching token row, reject if missing/used/expired, lock user row, set `used_at`, transition `pending_verification -> verified`, treat already-verified user as idempotent only if the token is the same valid unused token or return a clean “already verified” response after consuming/invalidating outstanding tokens. Password setup transaction: lock user, require `verified` unless using a combined verified setup token, require no existing `password_hash` for “initial” setup, write hash, transition `verified -> active`.

The risky edges are mostly races and partial failures. Token reuse should fail because `used_at` is checked and set under row lock. Expiry should be evaluated inside the consume transaction. Concurrent verification attempts should result in one successful consume and one “already used/invalid” response, not two transitions. A race between verification and password setup is handled by requiring `users.status = 'verified'` under lock before password write; if the UI gets ahead, return “verify email first” and let the client retry. Signup must be idempotent around the unique email constraint: retrying after a network timeout should not create duplicate users or duplicate active accounts. If the user row is created but email send fails, don’t roll back the user; record/send via an outbox or `verification_email_status`, and expose a resend path. The main ordering I’d use is: introduce statuses/token table behind the existing function, extract token issuance and mail send, extract verification consume, then extract password activation, with compatibility wrappers until routes/controllers are switched over.

## ordering_and_migration_plan *(voice: codex)*

I could not see the actual app source under `/private/tmp`, so treat this as an execution ordering plan rather than code-specific advice. I’d sequence it as an expand-and-contract migration, with every deploy shippable: first add the new signup state fields/token table as nullable/additive only, and dual-write them behind a flag like `auth.signup.write_v2_state` while all reads still use the old monolith state. This migration should be backfill-safe, not blocking: add columns/tables/indexes, deploy no-op/dual writes, run an idempotent backfill in batches, then add observability comparing old-derived state to new state. Rollback is flag-off plus leaving the additive schema in place. Test gate: migration smoke test, idempotent backfill test, and parity tests that old users, new users, expired tokens, reused tokens, and partially completed signups produce equivalent effective state.

Next extract behavior inward before changing routes. Pull email verification into a separate function/service, but keep the monolith as its only caller at first; feature-flag only the internal call path if needed, for example `auth.signup.use_extracted_verification`, not user-visible behavior. Rollback is switching the monolith back to inline logic. Gate this with characterization tests around existing verification behavior: token lookup, expiry, already-verified users, duplicate submission, transaction boundaries, audit/email side effects, and exact response semantics. Then do the same for initial password setup: extracted function called by the monolith, flaggable internally, with tests for token validity, password policy, hash creation, status transition, replay, and “verified but no password yet” versus “password set but verification not complete” if that state can exist during migration.

Only after both extracted functions are proven through the monolith would I split the HTTP layer. Add new routes/controllers for signup start, verify email, and set password, but initially route them to the same extracted services and keep the old endpoint live. Put traffic migration behind a route/client flag such as `auth.signup.use_split_flow`; server-side, support both old and new tokens/statuses until the old route is drained. This is the riskiest behavioral step because clients, links in emails, and in-flight users may straddle versions, so the rollback path must be “send clients back to old route, old route still accepts all current tokens.” Test gate: contract tests for old and new endpoints, link compatibility tests for emails generated before and after the deploy, end-to-end signup across mixed versions, and metrics proving no increase in abandoned/invalid-token signups.

The monolith removal is last and should be treated as cleanup after a measured drain period, not as part of the route split. Before deleting it, require that no current email links or clients depend on the old endpoint, backfill/parity mismatch is zero or explained, and dashboards cover each step of the split flow. The final schema contraction, if any, is blocking only after retention windows expire: make new fields non-null, drop old status/token fields, and remove dual-write code in separate deploys. Rollback after deletion is expensive, so the practical rollback is before deletion: keep the monolith callable but dark for at least one release. My main question for the doer: are verification tokens and password-setup tokens currently the same artifact? If yes, split token purpose/type early in the additive schema, because token confusion is the easiest security regression to ship during this refactor.

## risk_narrative_and_ux_continuity *(voice: claude)*

## Risk narrative & UX continuity

The function you're splitting is currently a single atomic story for the user: "I signed up." When you decompose it into signup → verify → set-password, you create *intermediate states the user can live in* — and intermediate states are where users get stuck, support gets paged, and trust gets eroded. Below is the failure landscape, narrated from the two seats that actually feel the pain.

### From the user's seat

The two stuck states matter more than the happy path. **"Verified but no password"** happens when a user clicks the email link, sees a confirmation, closes the tab (interruption, kid, meeting), and comes back the next day going "did I finish?" If they try to log in, the error has to be empathetic and *actionable* — not "invalid credentials" (they'll think they got hacked), but something like "Your email's confirmed — you just need to finish setting your password" with a button that re-sends the setup link. The worst version of this is silently treating them as a new signup, because now they have two half-accounts and support has to merge them. **"Password set but unverified"** shouldn't really exist if you order things correctly (verification gates password setup), but if you allow password-first for UX reasons, the login flow needs to surface "check your inbox" prominently and offer a resend — and the resend has to be rate-limited per-account, not per-IP, or one user on hotel wifi locks out the floor.

Email deliverability is the silent killer here. Roughly 1–3% of transactional emails just don't arrive (spam, corporate filters, typos in the address). The recovery UX needs three things: a visible "didn't get it?" link on the post-signup screen (not buried), a "change my email address" escape hatch *before* verification succeeds (because if they typo'd, the current account is unrecoverable without support), and a clear resend cooldown shown as a countdown ("resend available in 0:42") rather than a silent no-op button. The emotional shape across the funnel should escalate gently: signup success is celebratory, the "check your inbox" screen is calm and instructional, the first failed verification is reassuring ("links expire after 24h — here's a fresh one"), and only the *repeated* failures should suggest "contact support." Never blame the user for a typo without offering the fix in the same sentence.

### The verification email itself

This is the artifact that has to do the most work with the least real estate. It needs: a clear sender name (not `no-reply@`), a subject line that survives preview panes ("Confirm your email for [Product]" — not "Action required"), one primary CTA button, the full URL as fallback text below it (corporate clients strip buttons), an explicit expiration ("This link expires in 24 hours"), and a "didn't sign up? ignore this email" line at the bottom — *not* "click here if this wasn't you," because that's a phishing pattern and you're training users wrong. Avoid "Welcome!" framing in the verification email — save the welcome for after password setup, when they're actually in. And critically: when a user clicks an expired link a week later, do *not* show a dead-end error. Show "This link expired — want a new one?" with a single button. The number of users who give up at expired-link dead-ends is genuinely large.

### From on-call's seat

The pages you'll get clustered into a few shapes. **"I can't log in"** tickets will spike during the rollout — half will be the verified-no-password people, so build a runbook query (`SELECT user WHERE email_verified=true AND password_hash IS NULL`) and a one-click "resend setup link" admin action *before* you ship, not after the first page. **"I never got the email"** is the second cluster — you'll want a dashboard panel showing verification-email send/delivery/bounce/click rates segmented by email provider domain, because when Outlook starts greylisting you it's invisible until the dashboard catches it. **"I signed up twice"** will happen because users who don't get the first email try again with the same address — decide now whether the second signup attempt resets the verification token or returns "we already sent you one, check spam." Both are defensible; just pick one and make the error message match.

There's also a subtle data-integrity hazard: if signup creates the user row but verification/password-set happen later, you have rows in your DB that aren't real users yet. Anything that joins on the users table — analytics, billing, even welcome-email cron jobs — needs to filter on `status = 'active'` or you'll send "happy 1 month anniversary!" emails to people who never finished signing up. Audit those join sites before flipping the new flow on.

### Release notes & internal comms

For support: send a Slack message **the day before rollout**, not the day of, with three things — (1) the new states a user can be in and what each one looks like in the admin tool, (2) the canned response macros for the three top ticket shapes above, (3) the admin actions available (resend link, manually verify, reset password). Pin it. Don't make support discover the new flow from an angry ticket. For users, the release-notes framing should not mention the decomposition at all — they don't care about your refactor. If anything externally-visible changed (an extra screen, a new email), frame it as a security improvement ("we've added an extra step to keep your account safe") rather than a process change. For the engineering changelog, *do* document the state machine explicitly with a diagram, because the next engineer who touches this in 18 months will not remember why the states exist.

One follow-up worth raising with the other slices: the ordering decision (verify-then-password vs. password-then-verify vs. parallel) is partly a UX call and partly a security/abuse call — those slices should compare notes, because "verify first" is friendlier for legit users but creates an email-enumeration oracle, and "password first" is the opposite. Whoever owns the security slice and whoever owns the ordering slice should explicitly converge on that tradeoff rather than each assuming the other's default.
